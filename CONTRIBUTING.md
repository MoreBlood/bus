# Как присылать изменения

Коротко: ветка или форк → PR в `main` с заголовком «тип: описание» → живое превью и зелёный CI →
одобрение → squash-мерж → Vercel сам выкатит на https://bus.akapps.click.

## Заголовок PR

После squash-мержа заголовок PR становится коммитом в `main` и строкой в [CHANGELOG.md](CHANGELOG.md),
поэтому он в формате [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/): `тип: описание`
или `тип(область): описание`, описание — по-русски.

| Тип | Когда | Версия |
|---|---|---|
| `feat` | новая возможность для участников | минорная (0.**2**.0) |
| `fix` | исправление | патч (0.1.**1**) |
| `perf` | быстрее без изменения поведения | патч |
| `deps` | обновление зависимостей (так подписывает Dependabot) | — |
| `docs`, `refactor`, `test`, `ci`, `build`, `style`, `chore` | всё, что участники не заметят | — |

Ломающее изменение — `feat!: …` и строка `BREAKING CHANGE: …` в описании PR.

Примеры: `feat(журнал): фильтр по участнику`, `fix: разрыв одометра у многодневных поездок`,
`docs: как подключить ассистента`. Проверка «Заголовок PR» в CI не пропустит другой формат.

## Превью PR

Vercel собирает каждый PR и оставляет в нём ссылку на превью. Превью работает на **отдельной
превью-базе с демо-данными**, вход там выключен, MCP открыт — можно спокойно тыкать. Боевая база и
боевые секреты превью недоступны. Превью-база общая для всех PR; если другой PR успел поменять схему,
сборка превью пересоздаст базу с нуля (данные всё равно демо).

PR из форка Vercel соберёт после того, как владелец нажмёт «Authorize» в комментарии Vercel.

## Версии и релизы

Версия — [SemVer](https://semver.org/lang/ru/), теги `vX.Y.Z`. Всё делает release-please:

1. После каждого мержа в `main` он обновляет релизный PR «chore(main): release X.Y.Z» — там
   новая версия, записи в `CHANGELOG.md` из заголовков вмерженных PR.
2. Когда хочется выпустить версию — мержим релизный PR. Появляются тег `vX.Y.Z` и релиз на
   GitHub с тем же текстом.

Сайт от релизов не зависит: каждый мерж в `main` выкатывается сразу. Версия — это отметка «что вошло»,
её видно в приложении внизу раздела «Участники». Теги `v*` защищены от удаления и перезаписи.

## Перед началом

```bash
npm install && npm install --prefix web
npm run demo   # вымышленные данные в локальной базе
npm run dev    # http://localhost:5173
```

Node 22 (`.nvmrc`). Вход локально выключен, вы — админ.

## Правила `main`

`main` защищён — сломать его нельзя:

- прямые пуши в `main` запрещены, только через PR;
- мерж — только squash (одна аккуратная запись в истории на PR) и только при зелёной проверке
  **«Готово к мержу»**;
- ветка PR должна быть свежей относительно `main` (кнопка «Update branch» в PR);
- нужно одно одобрение ревьюера; все обсуждения в PR должны быть закрыты;
- после мержа ветка удаляется сама; можно включить auto-merge — PR влетит сам, когда всё станет зелёным;
- заголовок PR — в формате «тип: описание» (см. выше).

## Что проверяет CI

| Проверка | Что внутри |
|---|---|
| Заголовок PR | формат «тип: описание» — из него собирается чейнджлог |
| Сервер — типы и тесты | `tsc`, тесты расчётов журнала, HTTP API и MCP на временной базе |
| Фронт — линтер и типы | Biome, `tsc` |
| База — миграции и схема | миграции согласованы; схема не изменена без миграции; миграции и демо-данные на пустой базе |
| Сборка как на Vercel | `npm run build` — ровно то, что выполнит продакшен |
| **Готово к мержу** | все проверки зелёные — обязательная проверка для мержа |

Локально то же самое (кроме сборки): `npm run check`.

## Схема базы

Меняете `src/db/schema.ts` → `npm run db:generate` → коммитите `drizzle/` вместе с кодом. Миграции
применяются к боевой базе при сборке из `main`; сломанная миграция уронит сборку, и сайт останется на
прошлой версии.

## Стиль

- Интерфейс и комментарии — по-русски.
- Логика — в `src/service/`, её зовут и API, и MCP.
- Дизайн — словарь из `DESIGN.md`: жёлтое только на полосе, главном действии и активной навигации.
- Заголовки PR — «тип: описание по-русски», коммиты внутри ветки — как удобно (в `main` попадёт заголовок PR).
